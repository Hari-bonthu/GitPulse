## Architecture Pre-Check Summary

Before writing these plans, a full system architecture audit was performed:

- **Backend**: FastAPI 0.115 + GitPython 3.1.43 + Pydantic v2. All mutation
  functions follow `Tuple[bool, str]` return convention. Imports use
  `from models import *` wildcard in `git_scanner.py`.
- **Frontend**: Vanilla JS SPA with centralized `api()` fetch wrapper,
  `state` object for all view state, and `Toast` (Sonner-style) for feedback.
  All DOM is dynamically rendered via JS template literals.
- **Design System**: Emil Kowalski motion curves (`cubic-bezier(0.23, 1, 0.32, 1)`),
  Lucide-only SVG icons, dark/light theme via CSS custom properties,
  `.custom-dropdown` popover pattern for interactive menus.
- **Existing Gaps Identified**:
  - `git_scanner.py`: No `list_branches`, `checkout_branch`, `fetch_remote`,
    `pull_changes`, `discard_file_changes`, `discard_all_changes`, or
    `create_stash` functions.
  - `models.py`: No `BranchItem`, `CheckoutBranchRequest`, `CreateStashRequest`,
    or `DiscardRequest` models.
  - `app.py`: No `/branches`, `/branches/checkout`, `/fetch`, `/pull`,
    `/discard`, or `POST /stash` (create) endpoints.
  - `app.js`: Branch bar is static text. No branch picker, fetch/pull
    buttons, discard controls, or stash creation form.

## Dependency Notes

- **002 requires 001** because the branch picker UI calls `GET /repos/{id}/branches`
  and `POST /repos/{id}/branches/checkout`, and the Fetch/Pull buttons call
  `POST /repos/{id}/fetch` and `POST /repos/{id}/pull`.
- **003 requires 001** (partially) because Plan 001 Step 1 adds the
  `CreateStashRequest` and `DiscardRequest` models to `models.py`. If
  executing Plan 003 independently, those models must be added in Step 1.
- **004 requires 003** because the discard and stash creation UI calls
  `POST /repos/{id}/discard` and `POST /repos/{id}/stash`.
- **002 and 003 are independent** of each other and can be executed in
  parallel if desired (on separate branches). However, 003 should verify
  models from 001 exist first.

## Recommended Execution Sequence

```
001 (backend: branches + sync)

 └── 003 (backend: discard + stash create)
      └── 004 (UI: discard + stash create)
```

Optimal path: execute 001 → then 002 and 003 in parallel → then 004.
Conservative path: execute 001 → 002 → 003 → 004 sequentially.

## Findings Considered and Rejected

- **Git graph (DAG) visualization**: Not worth doing in Phase 1/2 — requires
  significant SVG rendering work with no backend dependency, and can be
  tackled independently later.
- **System tray daemon**: Out of scope for Phase 1/2 — requires `pystray`
  dependency and is an independent feature.
- **Side-by-side diff viewer**: Low leverage for Phase 1/2 — the existing
  unified diff viewer is functional. Can be improved in Phase 3.
- **Multi-repo batch actions**: Low urgency — individual repo operations
  must be stable first before batching them.
